# Key Management Service (KMS)

* Is a Public Service and is isolated to a region
* Create, Store and Manage cryptographic Keys (which can be used to convert plaintext to ciphertext and viceversa)
* Is capable of handling both symmetric and asymmetric Keys
    * Symmetric: uses a single shared secret key for both encrypting and decrypting data. Both the sender and receiver must possess this exact same key
    * Assymetric: uses a mathematically related pair of keys: a public key (shared openly to encrypt data) and a private key (kept secret to decrypt data
* Is capable of performing cryptographic operations (encrypt, decrypt, ...)
* Keys never leaves KMS
* Provides FIPS 140-2 (L2) compliant service
* Support multi-region keys, where keys are replicated to other AWS regions
* Keys are either AWS owned or customer owned
    * AWS owned keys are a collection of KMS keys that an AWS service owns and manages for use in multiple AWS accounts
    * Customer Owned Keys
        * AWS managed: are created automatically by AWS when services such as S3 are used
        * Customer managed: are created explicitly by the customer to use directly in an application or within an AWS service. They are more configurable
* KMS keys support rotation, where physical backing material (the data used) is changed
* KMS keys contains the `Backing Key`, the physical key material and all previous backing keys caused by rotation
* Aliases for keys can be created, they are per region
* The account trust for KSM should be explicitly added on a key policy or not
* Key policies are a type of Resource Policy added individually to each key

## KMS keys

* Also refered as CMKs (customer master keys)
* Are used by KMS within cryptographic operations
* Can be thought of as logical containers - key ID, creation date, key policy (resource policy), description and state of the key
* Every KMS key is backed by physical key material
    * It's the data which is held by KMS, which is actually used to encrypt and decrypt things up to 4kb in size
    * The physical text material is stored in an encrypted form, not in plaintext
    * Can be generated by KMS or imported into KMS
* KMS keys are generally only used to work on small bits of data or to generate other keys

## DEKs (Data Encryption Keys)

* Are generated using a KMS key using the GenerateDataKey operation, this operation generates a `data encryption key` which can be used to encrypt and decrypt data which is more than 4kb in size
* KMS know which KMS key was used to create certain DEK, but KMS doesn't store the data encryption key
* Data encryption keys are linked to the KMS key which created them, but KMS doesn't store the data encryption key in any way
* When a Data Encryption Key is created, KMS provides you with two versions of that data encryption key
    * Plaintext version: Can be used inmediately to perform cryptographic operations, it should be discarded after being used
    * Ciphertext version: The Data Encryption Key is encrypted in KMS, this version can be given back to KMS for it to be decrypted
* KMS doesn't do the encryption or decryption of the date, that operation is performed by the user or service which is using KMS
* To decrypt the encrypted data, the encrypted data encryption key is given back to KMS, and using the same KMS key used to generate it, the plaintext version is retrieved. That decrypted version is then used to decrypt the data. After finished the use of that version it should be discarded
